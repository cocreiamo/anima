# Branching and releasing

How Anima is kept releasable at any time, given that some suites are too long
for every pull request and "passed the pull request checks" and "fit to
release" are different facts that need different names. How GitHub accepts the
settings is `anima-tech-github-governance`.

## Use this when

- Opening, titling or merging a pull request.
- Changing a workflow, the ruleset or the promotion.
- Moving `main-green`, preparing a release or choosing a version.
- Deciding what an environment may run.

## Rules

1. **One trunk.** `main` is the only long-lived development branch. Work happens on short-lived branches and reaches `main` through a pull request, squashed, through the merge queue; no direct push, no force push, no deletion of `main`. There are no release branches until a fix must be backported; a backport branch then starts from a released tag.
2. **Titles and commits follow Conventional Commits,** checked by `committed` on commits and by `amannn/action-semantic-pull-request` on titles; releases and the changelog are generated from them. Example: `feat: accept tokens from a second issuer`.
3. **`main-green` points to the newest commit of `main` that passed every suite.** Nobody commits to it; only the Promote workflow moves it, and only forward. The ruleset cannot enforce that yet: it forbids force pushes and deletion but cannot restrict who pushes (GAP-008).
4. **Two tiers of verification.** Pull request: the fast checks, `mise run check`. Promotion: everything, `mise run promote:verify`, including the suites too long for a pull request; it runs nightly and on demand. The engine's system tests (`mise run engine:test`) are in both: on a pull request and in the merge queue as the check `System tests` (`system-tests.yml`), which reports on every change and runs only when the change touches the engine, its configuration, its pinned sources, its tests or the commands of the workflows (R114); in the promotion on the commit being promoted, with the engine image built cold (R24).
5. **Releases come only from `main-green`** (R24). The version and the changelog are prepared on `main` by the `release-please` pull request (`prepare-release.yml`); the tag and the GitHub release are created by the Promote workflow (`promote.yml`) when the commit that carries the version is promoted. Not: a workflow named Release that only prepared a version (it became Prepare release).
6. **Build once, promote the artifact.** The images published for a release are the ones built and verified in the promotion run, identified by digest; nothing is rebuilt to be released, and a release build restores no cache. The Promote workflow archives the image that passed the system tests, a separate job that holds `packages: write` loads it, checks its id against the one that passed and pushes it to `ghcr.io/cocreiamo/anima` under the version, recording the digest that the release notes state; a tag that exists is never moved: the release then points at the digest it already holds and its notes say so (an interrupted release is finished, not repeated), and `latest` is never written (R115). The same pinned sources must also produce the same image, bit for bit, so that building again checks what was promoted (R47).
7. **Environments run released versions only.** Staging and production are given a version and its digests, never a branch or a commit.
8. **Versions follow Semantic Versioning 2.0.0.** A published tag is never moved or reused: before pushing an image tag the promotion asks the registry and stops when it cannot tell whether the tag exists, since "cannot tell" is not "does not exist" (PM-013, R115). Until the founder decides otherwise the first release is 0.0.1 and every release stays in 0.0.\*: only the patch number is raised, whatever the commit type, a breaking change included. The release configuration holds it durably: `initial-version` sets the first release (without it release-please proposes 1.0.0 when no release exists yet, whatever the manifest says) and the `always-bump-patch` versioning strategy sets every later one (R110); a one-shot `release-as` is not used.
9. **When `main` breaks, revert first.** The offending change is reverted and comes back through a new pull request. A failed promotion blocks every later release until `main` is fixed or reverted, which is the intended pressure.
10. **A workflow is pinned and least-privileged:** actions by commit SHA, minimal `permissions`, no untrusted input in a shell, `zizmor` clean. A workflow that provides a required check also runs in the merge queue.
11. **Only the founder commits, pushes or changes a repository setting** (`anima-repository-conventions`). A setting that cannot be a file is a founder task in the backlog.
12. **System tests run on GitHub-hosted runners, with a cache of the inner images on pull requests.** Observed on 2026-11-28 on a plain `ubuntu-24.04` runner with the rootless container runtime as installed, no privileged mode and no change to the runner: the system tests pass; a cold job took 23 to 40 minutes, the build of the identity provider dominating and varying, and 9.5 minutes with the six inner images restored from a cache made with `podman save --multi-image-archive` and `actions/cache`, keyed on the submodule status and on `engine/`, `mise-tasks/engine/` and `config/`. Not: caching the runtime's storage directory (it does not work), or the engine image itself (not worth it). Pushes to `main` save the cache; pull requests and the merge queue only restore it; the promotion restores none. The key, the load and the save are commands (`ci:cache-key`, `ci:cache-load`, `ci:cache-pack`, R170, R171): the save removes an archive in the way itself, since the tool refuses to write over one (PM-010).
13. **Files the release tool writes are not ours to format.** The changelog has the tool's own layout, which Prettier rejects and the tool cannot change, so it is in `.prettierignore` and covered by `REUSE.toml` (R155, PM-012). A new file the tool writes goes through the same: apply its diff locally and run `mise run check` before it is first opened. A pull request opened with the workflow's token starts no workflows (GitHub's rule against recursion), so the release pull request shows no checks until a person or agent closes and reopens it; this holds until the organization's App opens it (TASK-58, TASK-53).
14. Unverified: **the release path.** The promotion's build, test and publish path (R24, R115) has been read, not run: the first run on `main` with a prepared version shows it, and so does that a pull request or the merge queue can read the cache saved from `main`, that the registry accepts the push, and that a release created with notes and generated notes carries both. The ARM image, the bill of materials and the attestation are not built (R16, R23).
15. Unverified: **that the ruleset is applied on GitHub.** The rulesets are files in `.github/rulesets/`; their being applied is a GitHub setting that no test of this repository verifies.
16. **A workflow step is one call of a command that has a test (R168).** Shell written inside a workflow cannot be run on a machine, so it first runs in production: three times on 2026-11-28 (PM-010, PM-013 and the first publishing run). A `run:` is one or more lines, each exactly `mise run <task>` followed by literal words or `"$NAME"` of the step's environment, and nothing else: no other command, no pipe, `&`, `;`, redirect, substitution, comment, conditional, option of the shell or `${{ }}` (an expression reaches a command through `env:`). Whatever decides, parses or calls a tool is in the command: a file task in `mise-tasks/<area>/` (`ci` for the workflows' own), which takes its input from its environment and arguments and gives a value to the workflow on standard output or as one `name=value` line appended to `$GITHUB_OUTPUT`. Each command has a test that runs it for real against the real tool, and the tests that need containers are in `tests/ci/`, run by `mise run ci:test` in the System tests job on every change to the commands and never in `mise run check` (R55): podman for the cache of images, git for the key, the copy tool against a throwaway registry started from its pinned image. The platform's own API has no stand-in: its commands are run with a stub `gh` that answers with a response recorded from the platform, and a test says so where it does that. Example: `system-tests.yml` and `mirror-base-images.yml` (`ci:changes`, `ci:cache-key`, `ci:cache-pack`, `ci:mirror-copy`). Not: a `run: |` with a function, a pipe or an `if`; a test that reads the text of a command instead of running it; a decision taken by a step before the checkout of the repository. Until it is converted `promote.yml` is the one dated exception (`tests/repository/test_workflow_steps.py`). The reusable workflows of the organization (`cocreiamo/.github`) still hold shell, in `check.yml` (the checkout of submodules and the key of the cache); converting them is a change of that repository.
17. **The job that holds a credential to write runs no tool of the repository and one command.** The job of the mirror that holds `packages: write` runs the checkout (without credentials), the task runner with no tool installed (`install: false` and `MISE_TASK_RUN_AUTO_INSTALL: "false"`, which stops `mise run` installing the tools of `mise.toml`, observed locally) and `mise run ci:mirror-copy`, whose copy tool is the pinned image of the register (R163). Not: installing the repository's tools in it.
18. Unverified: **the converted workflows have not run on GitHub.** The commands are run here for real (R169 to R174); that the platform accepts the calls as the workflows now make them is shown by the first runs: the checkout and the task runner before the decision of `system-tests.yml` (and that `install_args: jq` installs only that tool), the `install: false` input of the task runner, the checkout and the registry login in the mirror job, and the fork sync with its token inside a job that checks out the repository.

## Questions to answer before proposing

- Does the change reach `main` through a pull request with a Conventional Commits title?
- Is the check fast enough for a pull request, or does it belong to the promotion?
- Does anything rebuild an image that was promoted, or run a branch in an environment?
- Does the version stay in 0.0.\* (patch bump only) until the founder decides otherwise?

## Where the result goes

Workflows and rulesets go to `.github/`; the tasks to `mise.toml` (`promote:verify`); a platform limit to `gaps.toml` (GAP-008). Related skills: `anima-repository-conventions`, `anima-tech-github-governance`, `anima-designing-for-production`.
