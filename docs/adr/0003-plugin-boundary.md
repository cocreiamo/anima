# Boundary between the core and plugins

## Context and Problem Statement

Agencies and third parties must be able to build on Anima without their work
falling under the AGPL, while every change to Anima itself stays open. The
boundary has to be precise enough to be checked by tools, not only stated in
a licence text.

How is the boundary between the core and the plugins drawn, so that agencies and third parties can build on Anima without their work falling under the AGPL, while every change to Anima itself stays open?

## Decision Drivers

- Agencies and third parties must be able to build on Anima without their
  work falling under the AGPL.
- Every change to Anima itself stays open.
- The boundary has to be precise enough to be checked by tools, not only
  stated in a licence text.

## Considered Options

- The Anima Plugin Exception under section 7 of the AGPL, with plugin rules
  enforced by Bazel `visibility`
- Nx to enforce the boundary between the core and the plugins

## Decision Outcome

Chosen option: "The Anima Plugin Exception under section 7 of the AGPL, with plugin rules enforced by Bazel `visibility`", because Nx would be a second build tool beside Bazel ([ADR-0006](0006-repository-and-toolchain.md)).

### Terms

"Core" in this ADR means Anima's own code other than plugins. It is not the
PostgreSQL fork of [ADR-0001](0001-hexagonal-architecture.md), nor any other forked component: each keeps its
own licence ([ADR-0002](0002-licensing-and-cla.md)).

### Licence boundary

The [Anima Plugin Exception](../../PLUGIN-EXCEPTION.md) is an additional
permission under section 7 of the AGPL.

1. Configuration and data are not covered by the licence. This is the same
   boundary as the one between the engine, which the product owns, and an
   instance's configuration, which the adopter owns ([ADR-0001](0001-hexagonal-architecture.md)).
2. A plugin, meaning a work that uses Anima only through its public
   interfaces, may carry any licence. The same holds for code generated by
   Anima's own tools.
3. Every modification of the core is AGPL, including one made so that a plugin
   can work.
4. Official plugins live in the core repository and are AGPL.

### Marketplace

The marketplace is built in and lists official plugins only. No third-party
marketplace is planned.

### Rules for official plugins

These rules are enforced by automated checks, not by convention.

1. Each plugin is a separate package in `plugins/<name>/` with its own schema,
   commands, views, widgets and tests.
2. The core never imports a plugin. Bazel `visibility` enforces this: a plugin
   is not visible to the core, so a core target that depends on one does not
   build.
3. Official plugins use only the public interfaces available to agencies. If
   something is missing, an interface is added; there are no shortcuts.
4. Plugins are disabled by default and are enabled per application.

### Consequences

- Good, because rule 3 makes the term "Interfaces" in the exception
  verifiable: what the official plugins use is, by construction, the public
  interface.
- Bad, because every capability an official plugin needs becomes a public
  interface that must be maintained.

### Confirmation

Not built. No plugin exists and there is no `plugins/` directory. The rules for official plugins say that they are enforced by automated checks, the rule that the core never imports a plugin by Bazel `visibility`; none of these checks exists yet and no requirement of the model verifies them.
